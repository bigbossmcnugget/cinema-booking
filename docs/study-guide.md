# Lumen: база, backend, frontend и подготовка к защите

Учебное пособие по объединённому проекту Cinema booking. Версия 27 октября 2026 года.

Этот разбор соответствует новой версии с PostgreSQL и 13 таблицами. Предыдущая реализация D1 перенесена в database/legacy-d1 и больше не обслуживает сайт. Исходный SQL из присланного архива сохранён отдельно, поэтому можно показать, какая модель была импортирована и какие изменения появились при реализации.

Документ помогает понимать проект, показывать работающий сценарий и отвечать по коду. Он не заменяет самостоятельный прогон и не является доказательством личного авторства каждой строки. Для подготовки важнее проследить одну бронь от кнопки до базы, чем запомнить названия всех библиотек.

## 1 Как один проект относится к разным предметам

В заданиях по базам данных сначала требуются язык backend, ORM, Docker и Faker-seeder; следующее задание добавляет индексы и план кеширования. Работа по клиентской встрече проверяет показ готового сценария, пользу приложения, планы развития и участие команды. Эти результаты можно представить на одном Lumen, но критерии каждой работы различаются.

Для базы показывай исходный SQL, ORM-схему, миграцию, seeder, количество строк и связи. Для frontend показывай компоненты, состояние и действия пользователя. Для backend показывай проверку входных данных, транзакцию и серверные права. Для клиентской встречи сначала показывай сайт и пользу, а уже затем отвечай о реализации.

Наличие красивого интерфейса не доказывает выполнение задания по Docker. Наличие docker-compose.yml не доказывает, что сайт использует эту базу. Полный технический сценарий должен пройти через один выбранный backend и одну базу.

## 2 Что именно было в архиве

Архив cinema-project-main.zip содержал SQL-схему PostgreSQL, README, две версии ER-диаграммы и вспомогательный PowerShell-скрипт. Готового HTTP backend, ORM-моделей, Docker Compose и Faker-seeder там не было. Поэтому корректно говорить: «Мы взяли исходную модель данных и реализовали её через ORM».

Файлы database/source/project.sql и диаграммы сохранены без изменения. Их происхождение записано в database/SOURCE.md. Автор исходного дизайна в архиве не был указан; имя участника нужно добавить по фактической договорённости команды. Импорт файлов своим коммитом не меняет автора их содержимого.

В database/project.sql лежит текущая схема, сгенерированная из Drizzle. Она отличается от исходной там, где добавлена гостевая бронь. Изменения перечислены в database/schema-mapping.md. PowerShell-скрипт из архива не запускался.

## 3 Как запустить версию для задания

Нужны Node.js не ниже 22.13, npm и Docker с Compose. Все команды выполняются из outputs/cinema-booking, где находится package.json. Ошибка No package.json found означает, что открыт другой каталог.

```sh
npm ci
cp .env.example .env
docker compose up -d --wait db
npm run pg:migrate
npm run pg:seed
npm run pg:verify
```

Затем в первом терминале запускается npm run api:dev, во втором — npm run dev. Сайт открывается по http://127.0.0.1:3000/, API слушает порт 3001. Vite пересылает запросы /api к backend. Если запущен только интерфейс, каталог не загрузится: теперь фильмы действительно приходят через API.

В compose используется PostgreSQL 17 и named volume cinema_postgres. Docker обычно добавляет к имени volume префикс проекта. Команда docker compose down останавливает контейнеры, сохраняя данные. Вариант down -v удаляет volume, поэтому его нельзя использовать как обычный перезапуск перед показом.

На этом компьютере Docker отсутствует. Миграции, seeder, запросы и браузерный сценарий проверены через PGlite — встроенный PostgreSQL. Это полезная проверка совместимости схемы и логики, но не выполненная проверка Docker Engine и сохранения volume.

## 4 Как запустить без Docker сейчас

Для локального показа предусмотрен отдельный понятный путь. Он использует ту же ORM-схему и миграции, а данные сохраняет в игнорируемой папке .data/postgres.

```sh
npm run demo:prepare
npm run api:local
```

В другом терминале запусти npm run dev. demo:prepare применяет миграции, заполняет пустую базу и проверяет результат. Если данные уже есть, он не стирает брони и не запускает seeder повторно. Seed охватывает 21 день начиная с дня первой загрузки; при показе значительно позднее нужны будущие сеансы или отдельная новая demo-база.

PGlite работает внутри одного процесса. Не запускай второй CLI-процесс против той же папки, пока api:local держит её открытой. Автоматические тесты используют отдельную базу в памяти и не меняют сохранённые брони сайта.

## 6 Почему TypeScript и Drizzle

TypeScript используется и для React-интерфейса, и для Node.js backend. Типы помогают заметить неправильную форму данных при разработке. Файлы .ts содержат обычную логику, .tsx позволяют описывать интерфейс через JSX. После сборки типы исчезают: внешний JSON всё равно надо проверять во время работы.

Drizzle описывает таблицы и связи в TypeScript, позволяет строить запросы и генерирует миграции. В backend/schema.ts pgTable задаёт таблицу, notNull — обязательность поля, references — внешний ключ, unique — уникальность, check — допустимые значения, index — индекс.

```ts
userId: bigint('user_id', { mode: 'number' })
  .references(() => users.id, { onDelete: 'restrict' })
```

Это поле хранит ссылку на пользователя. В обновлённой bookings оно может быть NULL для гостя. Сам тип number в TypeScript не создаёт внешний ключ: реальное ограничение создаёт миграция PostgreSQL.

## 7 Все 13 таблиц и отношения

users содержит demo-пользователей, movies — фильмы, genres — справочник жанров. movie_genres связывает фильмы и жанры отношением многие-ко-многим. cinemas содержит кинотеатры, halls — их залы, seats — места внутри залов. screenings связывает фильм с залом, временем, форматом и ценой.

bookings хранит заказ, tickets — конкретные места на конкретном сеансе. payments хранит тестовые платежи, favorites — избранное demo-пользователей, notifications — тестовые уведомления о бронях. Наличие этих таблиц не означает, что на сайте уже есть платежи, избранное, уведомления или регистрация.

У одного кинотеатра много залов, у зала много мест и сеансов. У фильма много сеансов. У брони много билетов. Внешний ключ tickets.booking_id указывает на существующую бронь; tickets.screening_id — на сеанс; tickets.seat_id — на место.

Составной первичный ключ movie_genres(movie_id, genre_id) не даёт дважды добавить один и тот же жанр к одному фильму. UNIQUE(screening_id, seat_id) в tickets не даёт создать два билета на одно место одного сеанса. Ключи ограничивают данные в базе независимо от того, какая кнопка нажата на сайте.

## 8 Изменения для гостевой брони

В исходной модели bookings.user_id был обязательным. Пользователь проекта попросил оставить сайт без регистрации, поэтому требовалось явно согласовать модель с этим сценарием. user_id стал nullable, добавлены guest_name, guest_email и уникальный reference для экрана подтверждения.

CHECK требует либо существующий user_id, либо оба гостевых поля. Ссылка на users и правило ON DELETE RESTRICT сохранены. Это изменение видно в ORM, сгенерированном SQL и таблице соответствия; исходный SQL не переписан задним числом.

Поле email является контактом заказа, а не подтверждённой личностью. Нет пароля, email-кода, пользовательской сессии или входа. Seed-пользователи имеют отключённый пароль-заглушку, который не является настоящим хешем для входа. API входа вообще отсутствует.

## 9 Миграции: как схема попадает в базу

Схема редактируется в backend/schema.ts. Команда npm run pg:generate вызывает drizzle-kit с PostgreSQL-конфигурацией и создаёт файл миграции и снимок схемы. SQL внутри миграции генерируется инструментом, поэтому задание «не писать создание таблиц вручную» соблюдается.

Команда npm run pg:migrate подключается к базе и применяет миграции. История позволяет не выполнять одну миграцию повторно. Автоматический тест применяет миграции дважды к пустой тестовой базе, чтобы проверить повторный запуск.

Не редактируй уже применённую миграцию ради нового поля. Меняй ORM-схему, генерируй следующую миграцию, проверяй её и применяй. database/project.sql — справочная копия текущего сгенерированного состояния, а не другой источник истины.

## 10 Faker-seeder и проверка demo-данных

В backend/seed.ts Faker генерирует имена, даты рождения, рейтинги, UUID и тексты. Три фильма, постеры, зал и сетка мест заданы как понятные fixtures. Это нормально: Faker нужен для правдоподобных тестовых данных, а не для замены всех реальных названий случайными словами.

Вставки идут по зависимостям: пользователи и фильмы, жанры и связи, кинотеатр, залы, места, сеансы, затем брони, билеты, платежи и уведомления. Идентификаторы берутся из returning после вставки, поэтому внешние ключи ссылаются на реальные строки, а не на угаданные числа.

Результат начального seeder: 100 users, 3 movies, 2 genres, 3 movie_genres, 1 cinema, 2 halls, 120 seats, 126 screenings, по 120 bookings/tickets/payments/notifications и 100 favorites. После ручной проверки сайта броней и билетов может стать больше 120.

Seeder запускается одной транзакцией и отказывается перезаписывать непустую базу. Это сохраняет существующие данные. Faker random seed фиксирован, но даты сеансов зависят от дня первой загрузки. Проверка pg:verify смотрит количество строк, подтверждённые внешние ключи, соответствие билетов залам и отсутствие пересекающихся сеансов.

## 11 Каталог и разделение интерфейса

app/page.tsx теперь собирает небольшие части страницы. CinemaHeader отвечает за шапку, Schedule — даты, FilmCatalogue — карточки, SearchDialog — поиск, MovieDialog — описание, BookingDialog — места и оформление. LanguageSwitcher переключает язык. MobileMenu отвечает за навигацию на узком экране.

Из задания про App.vue берётся принцип разделения, а не буквальное требование использовать Vue Router: наш сайт написан на React. Маршруты отдельного каталога или отдельной страницы покупки пока не нужны, поскольку работа идёт в одной странице с диалогами. Backend находится в отдельном Node-сервисе.

useCinema в lib/use-cinema.ts хранит состояния и отправляет запросы. После выбора даты effect запрашивает /api/catalog?date=... . Backend выбирает активные фильмы и реальные сеансы из PostgreSQL. lib/catalog.ts остаётся источником presentation fixtures и переводов для трёх фильмов; английское название, описание, цена и времена в выдаче берутся из базы.

useMemo вычисляет отфильтрованный список, filter выбирает данные, map рисует карточки. Поиск в диалоге и фильтр жанра текущего интерфейса работают по загруженному массиву; не нужно утверждать, что каждый ввод символа вызывает индексированный SQL-запрос.

## 12 Путь от кнопки времени до схемы мест

openBooking открывает диалог, сбрасывает предыдущий выбор и включает индикатор загрузки. Ключ сеанса собирается из постоянного film slug, даты, времени и города. Он не является паролем или подтверждением доступа.

```text
batman-1989|2026-10-27|17:00|tallinn
```

GET /api/bookings получает ключ. findShow проверяет формат, дату, наличие фильма и точного времени в базе, активность кинотеатра и зала, статус сеанса. Придуманный сеанс не создаётся автоматически. Цена и зал также возвращаются из найденной записи.

Занятые места приходят из tickets через связь с seats. В новой базе больше нет списка заранее захардкоженных занятых A3/B7: demo-занятость создаётся настоящими seed-билетами, например F10. Ответ о местах содержит Cache-Control: no-store.

## 13 React-состояния и выбор мест

bookingMovie хранит текущий фильм, bookingTime — время, bookingStep — seats, checkout или success. selectedSeats содержит временный массив вроде ['A1', 'A2']. unavailableSeats содержит занятые позиции из базы. seatsLoading и bookingSubmitting отражают незавершённые запросы. confirmationId хранит reference успешной брони.

```ts
setSelectedSeats(current =>
  current.includes(seat)
    ? current.filter(item => item !== seat)
    : current.length < 10 ? [...current, seat] : current
);
```

Повторный клик снимает выбор через filter. Новый клик создаёт новый массив через spread. Функциональный setter использует актуальное предыдущее состояние. Клиент не позволяет выбрать больше десяти мест, но сервер всё равно проверяет количество самостоятельно.

Пока место выбрано в React, оно не занято в базе. После обновления страницы временный выбор теряется. После успешной отправки брони билет уже находится в PostgreSQL и место останется занятым. При ошибке загрузки схема не должна позволять продолжить; кнопка повторной загрузки открывает актуальные данные.

## 14 Белая форма и отправка JSON

Простая форма находится в BookingDialog, оформление .checkout-dialog и .plain-checkout — в app/globals.css. Поля name и email используют нативные input. Timo Triisa внутри пустого поля — placeholder, а не уже заполненное значение. Для отправки имя надо ввести самому.

submitBooking вызывает preventDefault, читает FormData и отправляет POST /api/bookings. Отправляются только showtimeKey, customerName, customerEmail и seats. Клиент не передаёт доверенную итоговую цену, роль или статус.

TypeScript не проверяет HTTP автоматически, поэтому backend/service.ts использует Zod. Проверяются типы, длина имени, email, формат ключа, 1–10 разных мест, допустимые ряды и номера. Неизвестные поля отклоняются. Например, добавить role: ADMIN или totalCents: 1 в JSON недостаточно для повышения прав или изменения цены.

При успехе сервер возвращает reference, selected seats, totalCents и status. Интерфейс переходит к success только при наличии настоящего reference; запасного выдуманного номера LUM-DEMO больше нет. При конфликте выбор сбрасывается и посетитель получает возможность перезагрузить схему.

## 15 Транзакция и защита от двойной брони

createBooking начинает транзакцию Drizzle. Внутри повторно находит сеанс, получает активные места его зала и проверяет конфликтующие tickets. Цена берётся из screenings.base_price и умножается PostgreSQL как NUMERIC, а не принимается из запроса посетителя.

Затем создаётся bookings с гостевыми контактами и tickets для каждого выбранного места. Если вставка любого билета не проходит, транзакция откатывает всю бронь. Нельзя получить успешный заказ без его мест.

Предварительный SELECT полезен для понятной ошибки, но не решает гонку: два пользователя могут одновременно увидеть свободное место. Окончательная защита — UNIQUE(screening_id, seat_id). При конфликте PostgreSQL возвращает код 23505; backend переводит его в HTTP 409. Автоматический тест отправляет два запроса к одному месту и ожидает один успех и один конфликт.

Отдельные внешние ключи исходной схемы не доказывают все смысловые связи. Например, seat_id может существовать, но относиться к другому залу. Это проверяет сервис бронирования; verifier проверяет demo-данные. Для более строгой схемы можно в будущем добавить составные внешние ключи.

## 16 HTTP и серверные права

| Ответ | Значение в текущем API |
| --- | --- |
| 200 | Каталог, места, health или разрешённое изменение |
| 201 | Гостевая бронь создана |
| 400 | Неправильный JSON или поля запроса |
| 403 | Административное изменение запрещено |
| 404 | Не найден фильм, сеанс или endpoint |
| 409 | Место уже занято |
| 413 | Тело запроса превышает ограничение |
| 503 | База временно недоступна |

Скрытая кнопка не является защитой. backend/server.ts проверяет каждый запрос к /api/admin/ до изменения данных. Если private ADMIN_API_TOKEN не задан или слишком короткий, управление отключено. Если токен настроен, нужен правильный Authorization: Bearer ... . Сравнение выполняется на сервере; заголовок x-role: ADMIN не даёт доступа.

Токен нельзя помещать в client/Vite-переменную или коммитить. Это простой административный сервисный ключ, а не полноценная авторизация пользователей. Роли из demo-таблицы users не превращаются в HTTP-права сами по себе. Регистрацию и сложный личный кабинет мы не добавляли.

## 17 Индексы: что объяснять преподавателю

Индекс — дополнительная структура базы, которая может ускорять подходящие поиск, соединение и сортировку ценой дополнительного хранения и обновления при записи. Индекс задаётся через ORM, а не командой из интерфейса. Планировщик может выбрать последовательное чтение на маленькой таблице: это не обязательно ошибка.

idx_screenings_movie_start(movie_id, starts_at) подходит для поиска сеансов фильма в диапазоне дат. UNIQUE tickets(screening_id, seat_id) одновременно обеспечивает целостность и помогает получить занятые места сеанса. Индексы на tickets.booking_id и tickets.seat_id добавлены для ссылок, у которых не было ведущего индексного столбца.

idx_movies_title связан с сортировкой по названию и точным поиском. Обычный B-tree не гарантирует ускорение ILIKE или поиска подстроки. Исходный idx_movies_filters пока относится к будущим фильтрам; не говори, что текущая кнопка «Семейные» использует именно его.

В исходнике idx_screenings_hall_start дублирует уникальный индекс на той же паре hall_id, starts_at. Он сохранён для понятного сравнения, а избыточность отмечена в README. Решение удалить его можно принять после проверки планов. Нельзя обещать ускорение в три раза, если такого замера в нашем проекте не было.

## 18 Кеширование: план вместо выдуманной реализации

В текущем backend нет Redis и общего кеша; ответы отправляются с no-store. По присланному заданию реализация Redis дополнительная, а описание TTL и сброса обязательное. План находится в README.

Каталог на дату с фильтрами можно кешировать на 60 секунд, включая дату, запрос и жанр в ключ. Сброс нужен после изменения фильма, расписания или цены. Описание кинотеатра можно кешировать на час и сбрасывать при изменении адреса, текста или схемы зала.

Занятость мест сейчас не кешируется: её читают из базы, а при записи действует уникальное ограничение. Если позднее в каталог добавить количество свободных мест, бронь и отмена должны сбрасывать также соответствующий кеш каталога. Инвалидация должна происходить после успешной транзакции. Имена и email не должны попадать в общий кеш.

## 19 Jira, GitHub, Teams и история изменений

Jira хранит задачи и договорённости команды, GitHub — код, коммиты и review issues, Teams — сдачу ссылки каждым студентом. Это может быть один общий проект, но автоматическая интеграция не возникает из похожих названий. В двух присланных заданиях по базам Jira прямо не указана.

docs/jira-backlog.csv содержит заготовки задач для импорта. Они не созданы на вашей доске и не назначены выдуманным участникам. Когда есть настоящая задача и настроенная интеграция, её реальный ключ добавляют в ветку, коммит или PR. Текущую доску и требования отдельного предмета по Jira мы не видели.

В текущем GitHub-репозитории issues на момент проверки не было. Это не означает, что преподаватель не оставил замечаний в другом репозитории. Для каждого настоящего issue нужно проверить проблему, сделать исправление либо объяснить отсутствие проблемы и только затем закрывать.

## 20 Как подготовиться и показать за 15 минут

За первые 20 минут подготовки открой сайт и пройди гостевую бронь. Следующие 25 минут изучай схему: films, halls, seats, screenings, bookings, tickets. Затем 25 минут проследи openBooking и submitBooking в hook, ещё 30 минут — createBooking, transaction, unique и requireAdmin. Последние 20 минут посвяти seeder, indexes, cache и самостоятельному объяснению без чтения документа.

| Время показа | Действие |
| --- | --- |
| 0–2 минуты | Объяснить задачу посетителя и границы demo |
| 2–6 минут | Фильм, дата, сеанс, места, сумма и белая форма |
| 6–8 минут | Номер брони и занятость места после обновления |
| 8–11 минут | Предложения развития каждого участника |
| 11–14 минут | Клиент пробует, команда задаёт вопросы |
| 14–15 минут | Записать пожелания и согласовать следующий шаг |

Для проверки используй Timo Triisa и timo@example.test. Настоящие платежи и письма не выполняются. Каждый участник должен понимать общий путь данных и самостоятельно объяснить свою фактическую часть работы.

## 21 Вопросы и короткие ответы

### Где теперь хранятся фильмы и брони?

Рабочие записи находятся в PostgreSQL. Три фильма и переводы описаны также как presentation fixtures в lib/catalog.ts; сервис объединяет их с данными базы. Брони и билеты сохраняет backend, а не localStorage.

### Почему без регистрации есть users?

Таблица users входит в исходный дизайн и заполнена demo-данными. Для гостевой брони user_id может быть NULL, а имя/email сохраняются в самой брони. Вход на сайте не реализован.

### Что доказывают тесты и чего они не доказывают?

Они проверяют миграции и реальные PostgreSQL-запросы на PGlite, количество строк, основные связи, бронь, конфликт мест, валидацию и административный guard. Они не доказывают запуск Docker-контейнера на этом компьютере и не заменяют проверку production-развёртывания.

### Почему нужны и Zod, и TypeScript?

TypeScript проверяет код во время разработки. Zod проверяет полученный JSON во время работы. Внешний пользователь может отправить любой тип, независимо от наших TypeScript-интерфейсов.

### Почему нельзя просто спрятать кнопку изменения?

Пользователь может отправить HTTP-запрос самостоятельно. Поэтому backend должен отказать в запросе без разрешения. В проекте это показывает requireAdmin и тест запроса с поддельным заголовком роли.

### Что пока недоработано?

Нет настоящих платежей, отправки писем, отмены и автоматического истечения брони. Таблицы favorites и notifications не имеют пользовательских экранов. Нужны дальнейшие правила освобождения мест, производственная авторизация и проверка Docker-пути на установленном Engine.
