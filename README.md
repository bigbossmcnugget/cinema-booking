# Cinema booking

Учебный сайт кинотеатра Lumen на TypeScript и React.

Посетитель выбирает дату, фильм и сеанс, отмечает свободные места и оформляет бронь без регистрации. Есть поиск, фильтры по жанру и переключение EN / RU / ET.

## Как запустить

Нужен Node.js 22.13 или новее.

```sh
npm ci
npm run dev
```

Открыть http://127.0.0.1:3000/. Для проверки сборки: `npm run build`.

## Где что находится

- `app/page.tsx` — страница, поиск и оформление брони.
- `app/globals.css` — оформление.
- `app/api/` — запросы каталога и бронирований.
- `lib/catalog.ts` — фильмы.
- `lib/ui-copy.ts` — подписи на трёх языках.
- `lib/show-dates.ts` — даты ближайших семи дней.
- `db/`, `drizzle/` — схема и работа с локальной базой.

## Ограничения

Фильмы, сеансы и цены демонстрационные. Настоящая оплата и отправка билетов по почте не подключены. Номер брони показывается на сайте. Используется один кинотеатр в Таллинне.

## Backend и ORM

Backend написан на TypeScript: один язык используется для интерфейса и серверных обработчиков, что упрощает чтение проекта и описание типов. Drizzle выбран для описания схемы, связей и индексов в TypeScript; текущая база — Cloudflare D1 (SQLite). Обработчик бронирования пока выполняет параметризованный SQL напрямую, поэтому наличие Drizzle-схемы не означает, что все запросы уже сделаны через ORM.

Текущий локальный запуск не использует Docker. Compose, Faker-seeder и соответствие исходному `project.sql` пока не реализованы/не проверены; этот репозиторий ещё нельзя считать полностью готовым к заданию «backend, Docker, ORM schema and demo data». Подробный аудит и порядок доработки: [docs/coursework-map.md](docs/coursework-map.md).

## Индексы

Индексы объявлены через Drizzle в `db/schema.ts`, миграция хранится в `drizzle/`. Пока runtime также создаёт их через `ensureDatabase`; переход на единый запуск миграций остаётся задачей.

| Индекс | Назначение и использование |
| --- | --- |
| `bookings_reference_unique` (`reference`) | Обеспечивает уникальность номера брони; поиска брони по номеру в интерфейсе пока нет. |
| `booking_seats_showtime_seat_unique` (`showtime_key`, `seat`) | Запрещает двойную бронь одного места на одном сеансе; соответствует проверке конфликта при POST `/api/bookings`. |
| `idx_booking_seats_showtime` (`showtime_key`) | Соответствует GET `/api/bookings?showtimeKey=...`; может быть избыточным, потому что составной уникальный индекс выше начинается с того же поля. Перед сохранением обоих нужно сравнить планы запросов. |
| `idx_bookings_email_created` (`customer_email`, `created_at`) | Заготовка для будущего списка броней по email с сортировкой по времени. Текущая страница такой запрос не выполняет; индекс нужно пересмотреть при доработке. |

Поиск фильма и фильтр жанра сейчас работают по массиву `lib/catalog.ts` в браузере. Индекс базы их не ускорит; индексы фильтрации фильмов понадобятся после переноса каталога в базу и появления соответствующих запросов.

## План кеширования

Это план; фактический кеш и Redis пока не подключены. По заданию реализация кеша дополнительная, описание плана обязательное.

| Данные | Ключ и TTL | Когда сбрасывать |
| --- | --- | --- |
| Будущий каталог из базы | `catalog:{locale}:{genre}:{page}`, 5 минут | При изменении фильма, жанра, перевода или постера — все затронутые варианты списка. Сейчас каталог статический, отдельный серверный кеш не нужен. |
| Будущие сеансы на день | `screenings:{cinemaId}:{date}`, 60 секунд | При создании, переносе, удалении сеанса или изменении его цены. Если ответ содержит число свободных мест — также после успешной брони или отмены. |
| Описание кинотеатра и зала | `cinema:{id}:{locale}`, 1 час | При изменении адреса, описания или схемы зала. |
| Занятые места текущего сеанса | Пока без серверного кеша | Читать актуальную базу при открытии схемы и повторно проверять при записи. Добавить запрет HTTP-кеширования ответа при реализации этой политики. |
| Личные данные и подтверждение брони | Не помещать в общий кеш | Имя/email и персональные ответы не должны попадать в общий кеш каталога. |

Сброс кеша должен выполняться после успешного коммита изменения базы. Даже при наличии кеша окончательное решение о доступности места принимают проверка базы и уникальное ограничение при записи. Redis можно добавить позже, когда будут реальные кешируемые запросы; он не заменяет базу бронирований.
